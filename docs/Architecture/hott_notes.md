ok let's think more:
- Stroscot does not have types - we have logic programming and assertions. A "type" corresponds in Stroscot to an assertion that an argument or return value is in a certain set and a "type error" corresponds to a program that has no valid execution paths
- HoTT does have sets in the logical sense but it also has paths - and these paths are "higher order" in the sense that they are paths or transformations between proofs (terms). And so this seems connected to things like first-order and second-order logic where we allow variables that quantify over propositions. And so maybe somewhere in HoTT there is actually some semantic thing about how we quantify over variables.
- Stroscot does have pattern matching - and this is where things get tricky, because we have a complex semantics for pattern matching based on expressing a term rewriting relation as a logical set and then using logic programming semantics. And so in particular unification ends up being involved, and this "pattern matching without K" paper has an explicit modification of unification to support its semantics.
- Axiom K lets us collapse the paths and stuff but it is not clear we want to collapse things, if we want to properly implement HoTT we need to support higher inductive types
- Stroscot does not have the evaluation order problem GHC's coercions have, a failed assertion will truncate that logical path regardless of how it is evaluation
- Stroscot represents the "failed computation" as a logical effect, essentially the semantics maps an expression to a set of possible values rather than a single value. this is cleaner than zero-width values or weird things like that. conceptually a function forcing a coercion or whatever is part of its semantics, and the logic programming aspect is how it restricts its caller - the program does not continue past the function if it fails, but it uses the return value (or values) if it succeeds. This is kind of similar to GHC's proof-irrelevance in that it doesn't matter "why" a function succeeds, only that it does, and then execution ends up with a particular value.
- in HoTT, we now have paths, and erasing is not safe, so now the return value of the function matters - we actually use the paths that logic programming finds.
- it's unclear what HoTT actually is like, there are so many presentations and things floating around - like the cubical type theory, maybe it is useful and maybe it isn't. what's really a question is how invasive it would be to support one of these weird theories - in particular, is it even possible to integrate into Stroscot's linear-logic sequent calculus based IR, and also, would it be worth it? univalence being a stuck term is a problem, and it is not clear why any of these logics are better for programming
-  also dependent types are kind of irrelevant to Stroscot, they are just a more complex assertion checking problem
